This file contains every test we run on the agent, what was fed
into each one, what we expected back, and what actually came back.

There are three suites:
  PART 1  - the PARSER      : does it READ an email correctly?
  PART 2  - the REPLY ENGINE: does it ANSWER one correctly?
  PART 2B - the DIARY       : does it know where the customer
                              is and when the plumber is free?
  PART 3 - the WHOLE AGENT : does it work on REAL email, sent by
                             hand through Gmail?

Parts 1 and 2 are rewritten by run_all_tests.py every time it runs.
Part 3 is written by hand and is carried across untouched.

======================================================================
  THE REAL FINDING FROM GROUP B - MAIL THE AGENT CANNOT SEE
  Found by sending six emails and only four arriving. No test would
  ever have caught this, because every test until now handed the agent
  an email directly instead of making it go and find one.
======================================================================

  WHAT HAPPENED
    Six emails were sent in one batch. The agent processed four.
    The phishing one (B2) had been put straight into SPAM by Google
    and the agent never saw it. B4 was simply slow to arrive.

    Roshan dragged B2 out of Spam and back into the Inbox. The agent
    was run again and still did not see it - because dragging it out
    of Spam marks it as READ, and the agent only ever looks at UNREAD
    mail. Marking it unread by hand finally let the agent find it.

  WHY THE AGENT ONLY READS UNREAD MAIL
    That is deliberate and it is load-bearing. It is what stops the
    agent replying to the same customer over and over every minute of
    every day. Remove it carelessly and the first thing that happens
    is a customer gets forty identical emails.

  THE TWO HOLES THIS OPENS
    1. Anything Google decides is spam is invisible to the agent. A
       real customer whose enquiry is misfiled gets no reply at all.
    2. Anything already marked read is invisible. So if the plumber
       rescues a lead from his own spam folder - or simply opens his
       email on his phone before the agent gets to it - the agent
       walks straight past it and never replies.

  WHY THAT IS SERIOUS, NOT COSMETIC
    In both cases the plumber believes the agent handled it. There is
    no error, no warning, nothing in the review pile. The lead just
    quietly never gets a reply, and the customer rings somebody else.
    The whole product is sold on "every enquiry answered in 60
    seconds". This is the failure mode that breaks that promise while
    looking like everything is fine.

  STATUS: FIXED AND PROVEN ON REAL EMAIL the same day. Roshan asked for
  it to be fixed straight away rather than deferred, on the grounds that
  it will happen to a real client. See GROUP S below for the two tests
  that prove it.

  WHAT THE FIX ACTUALLY DOES
    The agent no longer uses Gmail's read/unread mark as its memory.
    It keeps its own private list of every message it has already dealt
    with, written to already-handled.txt, and looks at all mail from the
    last 3 days in BOTH the Inbox AND the Spam folder. Whether the
    plumber has opened something no longer has any bearing on whether
    the customer gets answered.

    The read/unread mark is still set on inbox mail after answering, so
    the plumber's unread count still means something. Spam is left
    strictly alone - the agent does not reorganise a folder it was never
    asked to touch.

  THE DANGER THAT HAD TO BE HANDLED
    On its very first run the agent's list is empty, so every old email
    in the mailbox looks new and it would answer months of history at
    once. Instead the first run writes down everything already there as
    "already dealt with", replies to nothing, and says so plainly on
    screen. Proven: the first run noted 15 existing messages and wrote
    no replies at all.

THREE THINGS WORTH KNOWING, NONE OF THEM A FAILURE

  1. All three customers were offered the SAME two slots - today 8-10am
     and today 10am-12pm. That is correct behaviour today, because the
     agent cannot yet see the plumber's diary. But it means if five
     customers write in overnight, all five are pushed at the same two
     slots and the plumber ends up double or triple booked. This is the
     calendar step we deliberately deferred, showing up in real output
     for the first time. It is the reason firm auto-booking must not be
     sold to a client until the calendar is connected.

  2. THE ZIP CODE ONLY GOT US HALF THE ADDRESS.  ***FIXED 18 AUGUST***
     Spotted by Roshan reading this output on 13 August 2026. No test
     caught it, because no test was looking for it.

     In the United States a zip code is five digits naming a postal
     area. It does NOT include the street or the house number. So when a
     customer gave no address, the agent ended up knowing roughly which
     neighbourhood they were in and nothing more - the plumber still
     could not drive to them.

     The old decision was to ask the zip first anyway, on the grounds
     that a stranger might not want to hand over their home address in
     the first message, and collect the street later in the AI step.

     REVERSED 18 August 2026. The agent now asks for the FULL STREET
     ADDRESS in the first reply, and offers NO appointment times until
     it has one.

     Why it was reversed: working out how long the plumber takes to
     drive there, and whether the customer is even inside his service
     area, BOTH need a street address - and both have to be settled
     before a time is promised. Under the old order the address arrived
     after the slot had been offered, which was circular. Roshan's
     clinching argument was traffic: zip codes cannot see it, so a
     journey the agent thinks is 30 minutes becomes an hour in the rain,
     the plumber misses the window, and the customer blames him.

     Why the privacy worry was overweighted: someone contacting a
     plumber is asking a stranger to come to their house. The address IS
     the job. And the agent now gives the reason when it asks - "we
     check it's inside the area we cover, and it lets us give you an
     arrival time we can actually keep."

     Six new reply-engine checks guard this. The old emails further up
     this file still show "Also, what's your zip code?" - that is the
     record of what was actually sent between 13 and 17 August, and it
     stays as it happened.

  3. leads.csv still has a leftover row at the top from an earlier
     session - a made-up customer called Dave Harris. Nothing is wrong
     with the agent; it is old practice data. Worth clearing before that
     file is ever shown to a real client, so they do not see invented
     customers in their own lead list.
